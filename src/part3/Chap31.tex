\section{Refactoring des précédents travaux}\label{sec:refactoring-des-precedents-travaux}

À l'instar de la première partie, le travail sur l'architecture logicielle du projet \gls{IBIS} porte en premier lieu sur le remaniement du code du stage
effectué sur le projet DISTRISIM, pour l'appropriation du sujet et la montée en compétences dans un premier temps, et pour la conception d'un code plus robuste supportant
un plus grand volume de données et différents modèles dans un second.

Comme c'est le cas dans le projet \gls{IBIS}, on appelle TST le code précédent présenté dans \cite{TST} pour les prochaines parties, et \gls{IBIS}-DISTRISIM le code récemment remanié.

TST est à l'origine un code de 1000 lignes écrit sur un fichier donnant des courbes prévisionnelles de
consommation d'énergie avec ou sans adaptation des paramètres du modèle aux données
de la période précédant celle de la prévision.
Ses entrées sont saisies séquentiellement et manuellement dans le terminal du programme.

Si le code livre des résultats intéressants sur les bâtiments étudiés \ref{tab:tstfinal},
    son architecture rend difficile la compréhension microscopique du comportement du modèle
    d'une part \textit{(en particulier la sensibilité d'un paramètre devant un résultat précis)}, et la généralisation des expériences d'autre part \textit{(notamment le lancement d'une série massive de calculs pour apprécier les sorties du modèle à plus grande échelle)}.

    Ce constat permet de commencer la refactorisation avec en premier lieu la répartition des
        fonctions existantes dans une arborescence à plusieurs fichiers.
    Le listing suivant montre l'architecture adoptée, à l'exception de la partie \texttt{data}
        stockée à l'extérieur des sources comme le suggèrent les lignes de conduite du
        développement propre.

    Ainsi, la fonction \texttt{main} (renommée \texttt{run\_computation}) peut être lancée avec des entrées de fichiers choisies dynamiquement.
    Ceci facilite son utilisation dans des notebooks Jupyter et donc le lancement de nombreux calculs avec différents paramètres\footnote{La plupart des figures présentées dans la première partie sont obtenues grâce à cette multiplication des calculs, trop fastidieuse pour être lancée dans la première version du code.}.

    L'arborescence du projet ébauchée, l'étape suivante est l'inspection des fonctions pour vérifier leur propreté, leur maintenabilité et la facilité à les faire évoluer.
    Autant que possible, ce procédé tente de s'appuyer sur les recommendations du livre de Robert C. Martin \cite{clean_code}, faisant figure de référence standardisée dans le milieu du développement du logiciel.

Le nombre de bonnes pratiques décrites dans cet ouvrage est particulièrement élevé et toutes ne sont pas forcément applicables simultanément, en particulier les exemples sont souvent tirés du développement web, un domaine généralement éloigné du calcul scientifique.
La synthèse la plus élémentaire des techniques de nettoyage du code donnée plus bas a tout de même guidé le développement et les réflexions autour d'\gls{IBIS} :

    \begin{itemize}
        \item Le nommage des variables doit être explicite.
        En particulier, allonger le nom d'une variable est généralement une bonne idée même si sa lecture peut sembler fastidieuse.
        \item Les fonctions, classes, méthodes et fichiers doivent être le plus court possible (une dizaine de lignes maximum) et chaque fonction doit remplir un seul objectif.
        En général, si une fonction dépasse ce nombre de lignes, alors elle peut être séparée.
        \item De même, le nombre de paramètres d'une fonction ne doit pas être supérieur à trois.
        \item Le \gls{TDD} reste la meilleure approche à la quasi-totalité des problèmes de programmation, aussi l'utilisation des tests doit être aussi fréquente que possible
        \item Les commentaires doivent être utilisés avec parcimonie et ne remplacent en aucun cas l'explication du code par lui-même.
        La raison d'être de nombreux commentaires est en effet la clarification d'éléments de code mal implémentés, avec pour finalité la présence dans le projet de deux informations floues plutôt qu'une explicite.
    \end{itemize}

        L'apport de ce travail de refactorisation est double : \begin{enumerate}
           \item Les résultats précédents ont pu être consolidés avec la généralisation du
               tableau \ref{tab:tstfinal} sur un seul bâtiment à l'ensemble du quartier étudié \ref{tab:mean_std_by_building_by_month}, sans que cette tâche soit rendue fastidieuse par une implémentation de code perfectible.
           \item Il est désormais possible de développer de nouveaux modèles ou de consolider
                                                                   celui existant en s'appuyant
                                                                   sur le projet actuel, sans
                                                                   avoir à en commencer un
                                                                   nouveau.
        \end{enumerate}

        \subsection{Implémentation de plusieurs cas test}\label{subsec:implementation-de-plusieurs-cas-test}

            La plupart des futures modifications envisagées pour \gls{IBIS} sont d'une ampleur bien supérieure à celles déjà effectuées.
            Ainsi, il est important de garder un aperçu des résultats du modèle à chaque étape de développement pour s'assurer de sa performance.
            Cette vigilance est mise en oeuvre avec l'introduction de tests basés sur le modèle actuel.

            Pour l'instant, le test principal implémenté est la reproductibilité des tableaux \ref{fig:heatmap} et \ref{tab:mean_std_by_building_by_month},
                rendue possible par leurs notebooks associés, lesquels sont implémentés de sorte à faciliter la modification de leurs fonctions d'entrée pour vérifier cette reproductibilité.

            Ainsi, chaque modification majeure future peut être validée par la vérification de sa sortie avec ces deux cas test.

\section{Versionning et gestion de projet}\label{ch:versionning-et-gestion-de-projet}

La refonte de TST dans le projet IBIS est accompagnée d'un framework de versionning
jusqu'alors inexistant, hébergé sur un GitLab interne au \gls{CEA}\footnote{La plateforme est par ailleurs très récente et en cours de développement.
     Dans ce contexte, le projet IBIS a pu servir de retour d'expérience à l'équipe de maintenance pour son amélioration continue.}

     création d'issues et à leur résolution pendant les phases de développement.
