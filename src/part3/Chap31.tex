Ce chapitre vise à donner un historique du développement d'IBIS, et présente ses différents composants en argumentant chacun des choix d'implémentation.
À l'instar des précédents chapitres portant sur les aspects de modélisation, celui-ci est challengé par les conclusions rendues dans le chapitre final \ref{ch:resultats-et-failles-d'ibis-:-une-synthese-apres-un-an-de-developpement}.
L'absence de renvoi explicite à la documentation du projet s'explique par le fait que celle-ci est produite dans un autre livrable, bien qu'un extrait soit donné à titre indicatif en annexe \ref{ch:ibisdoc} de ce rapport.

\section{Aperçu de l'architecture du projet}\label{sec:apercu-de-l'architecture-du-projet}

    Le schéma \ref{fig:IBIS_archi} se veut le reflet de la figure \ref{fig:IBIS_final_scheme} présentée en introduction du chapitre 5,
    le premier adoptant un point de vue développeur et l'autre un point de vue utilisateur.
    Les principaux modules d'IBIS sont représentés et permettent d'établir un cycle de vie complet pour une modélisation :
    \begin{enumerate}
        \item Les données sont récupérées et aggrégées depuis diverses sources, puis importées dans une base de données unique.
            Cette étape peut imposer d'émettre plusieurs hypothèses nécessaires au traitement des données \textit{(par exemple si l'on récupère des données multizones alors que l'on cherche à définir un modèle monozone)}.
        \item Les deux approches concurrentes, développées dans leurs classes respectives \texttt{BlackboxThermalSolver} et \texttt{GreyboxThermalSolver}, utilisent les données d'entrée d'une part et des paramètres de calcul d'autre part, également stockés dans la base de données, pour prédire le comportement thermique d'un bâtiment.
        \item Les données de sortie sont à leur tour stockées dans la base de données pour analyse\footnote{Les courbes de températures et de chauffage sont également récupérées mais stockées dans des dossiers classiques pour faciliter l'implémentation de la base de données.}.
    \end{enumerate}

    À plus bas niveau, le listing \ref{lst:tree} montre l'architecture complète d'IBIS, organisée selon les modules principaux \texttt{loaders} \textit{(API avec la base de données)},
    \texttt{models} \textit{(logique métier, modèles thermiques et équations associées)}, et \texttt{solvers} \textit{(résolution des modèles, optimiseurs et régresseurs)} et \texttt{output} \textit{(exportation des résultats dans la base de données et tracé des figures)}.

    \subsection{Point d'étape sur le refactoring des précédents travaux}\label{subsec:refactoring-des-precedents-travaux}
        D'un point de vue chronologique, IBIS connaît comme première phase et axe de travail la restructuration des travaux menés sur l'identification des paramètres de bâtiment en 2023.
        Ceux-ci, bien qu'efficaces et permettant de produire les figures \ref{fig:predictioncambridgetst} et \ref{tab:tstfinal}, sont limités principalement par leur incapacité structurelle à généraliser les résultats, ce qu'IBIS cherche à pallier.
        Un autre objectif majeur est l'amélioration de la modularité du code avec l'ambition de pouvoir facilement changer de source de données en entrée ou de modèle sans devoir modifier le code outre mesure.

        Ainsi, la première période de développement s'appuie autant que possible sur les lignes de conduite du code propre dressées dans \cite{clean_code} et est synthétisée par le tableau \ref{tab:comparaisonarchi}, qui compare
        les spécifications internes des deux projets après quelques semaines de développement d'IBIS, à données d'entrée et de sortie similaires.

        \begin{table}[h!]

                \begin{tabular}{lcc}

        L'apport de ce travail de refactorisation est double : \begin{enumerate}
           \item IBIS remplit sa promesse de pouvoir généraliser les résultats en reproduisant le tableau \ref{tab:tstfinal} puis en l'étendant à l'ensemble du quartier étudié \ref{fig:heatmap}, sans que cette tâche soit complexe ou fastidieuse;
           \item Il est désormais possible de développer de nouveaux modèles ou de consolider celui existant en s'appuyant sur le projet actuel, sans avoir à en commencer un nouveau.
        \end{enumerate}

\begin{lstlisting}[language=YAML, caption={Fichier \texttt{.gitlab-ci.yml} d'IBIS},label={lst:cicd}]
# GitLab CI/CD pipeline for the IBIS project
# The base image only provides Python 3.12, used solely to bootstrap uv.
# uv then downloads and manages the actual Python 3.13.7 runtime.

stages:
  - test

variables:
  UV_PYTHON_VERSION: "3.13.7"
  UV_CACHE_DIR: "$CI_PROJECT_DIR/.uv-cache"

unit_tests:
  stage: test
  image: python:3.12-slim

  cache:
    key: "$CI_COMMIT_REF_SLUG"
    paths:
      - .uv-cache/

  before_script:
    # Install uv with standalone installer
    - apt-get update -qq && apt-get install -y -qq curl ca-certificates
    - curl -LsSf https://astral.sh/uv/install.sh | sh
    - export PATH="$HOME/.local/bin:$PATH"
    - uv --version
    # Install and pin the required Python version through uv
    - uv python install "$UV_PYTHON_VERSION"
    - uv python pin "$UV_PYTHON_VERSION"

  script:
    # Install project dependencies (respects uv.lock if present)
    - uv sync --frozen
    # Run tests
    - uv run python tests/unit_test.py

default:
  tags:
    - python

  artifacts:
    when: always
    paths:
      - .uv-cache/
    expire_in: 1 week\end{lstlisting}

    \begin{bluebox}
        Ce test simple ne permet évidemment pas de couvrir l'ensemble du code et des fonctionnalités d'IBIS, bien qu'il détecte un certain nombre de dysfonctionnements simples, notamment sur la résolution d'équations différentielles par le solveur GreyBox, étape du projet la plus complexe.
        Les tests plus complets ne sont pas ajoutés en raison des limitations techniques de l'instance GitLab du CEA, en particulier à cause du nombre limité de runners disponibles\footnote{Des travaux sont en cours pour intégrer d'autres runners à l'échelle Institut ou Laboratoire.}.
        En effet, un seul runner étant accessible à l'échelle CEA, celui-ci a un timeout capé à 30 minutes, empêchant le lancement de tests plus longs comme MEBM et AMSBP\@.
    \end{bluebox}
