\section{Refactoring des précédents travaux}\label{sec:refactoring-des-precedents-travaux}

    Le travail sur l'architecture logicielle du projet \gls{IBIS} s'est articulé dans un premier temps sur le remaniement du code du stage
    effectué sur le projet DISTRISIM dans l'optique de concevoir un code plus robuste supportant
    un plus grand volume de données et différents modèles ensuite.

    Pour la suite, on appelle TST le code précédent présenté dans \cite{TST}.

    TST est à l'origine un code de 1000 lignes écrit sur un fichier donnant des courbes prévisionnelles de
    consommation d'énergie avec ou sans adaptation des paramètres du modèle aux données
    de la période précédant celle de la prévision.
    Ses entrées sont saisies séquentiellement et manuellement dans le terminal lancé par son script principal.

    Si le code livre des résultats intéressants sur les bâtiments étudiés \ref{tab:tstfinal},
        son architecture rend difficile la compréhension microscopique du comportement du modèle
        d'une part \textit{(en particulier la sensibilité d'un paramètre devant un résultat précis)}, et la généralisation des expériences d'autre part \textit{(notamment le lancement d'une série massive de calculs pour apprécier les sorties du modèle à plus grande échelle)}.

    Ce constat permet de commencer la refactorisation avec en premier lieu la répartition des
        fonctions existantes dans une arborescence à plusieurs fichiers.
    Le listing suivant montre l'architecture adoptée, à l'exception de la partie \texttt{data}
        stockée à l'extérieur des sources comme le suggèrent les lignes de conduite du
        développement propre.

    Les sources sont ainsi pensées pour être lancées dans des notebooks Jupyter et ainsi permettre de nombreux calculs avec différents paramètres.

    L'arborescence du projet ébauchée, l'étape suivante est l'inspection des fonctions pour vérifier leur propreté, leur maintenabilité et la facilité à les faire évoluer.
    Autant que possible, ce procédé tente de s'appuyer sur les recommendations du livre de Robert C. Martin \cite{clean_code}, faisant figure de référence standardisée dans le milieu du développement du logiciel.

    Le nombre de bonnes pratiques décrites dans cet ouvrage est particulièrement élevé et toutes ne sont pas forcément applicables simultanément, en particulier les exemples sont souvent tirés du développement web, un domaine généralement éloigné du calcul scientifique.
    La synthèse la plus élémentaire des techniques de nettoyage du code donnée plus bas a tout de même guidé le développement et les réflexions autour d'\gls{IBIS} :

    \begin{itemize}
        \item Le nommage des variables doit être explicite.
        En particulier, allonger le nom d'une variable est habituellement une bonne idée même si sa lecture peut sembler fastidieuse.
        \item Les fonctions, classes, méthodes et fichiers doivent être le plus court possible (une dizaine de lignes maximum) et chaque fonction doit remplir un seul objectif.
        En général, si une fonction dépasse ce nombre de lignes, alors elle peut être séparée.
        \item De même, le nombre de paramètres d'une fonction ne doit pas être supérieur à trois.
        \item Le \gls{TDD} reste la meilleure approche à la quasi-totalité des problèmes de programmation, aussi l'utilisation des tests doit être aussi fréquente que possible
        \item Les commentaires doivent être utilisés avec parcimonie et ne remplacent en aucun cas l'explication du code par lui-même ni une documentation complète.
        La raison d'être de nombreux commentaires est en effet la clarification d'éléments de code mal implémentés, avec pour finalité la présence dans le projet de deux informations floues plutôt qu'une explicite.
    \end{itemize}

        L'apport de ce travail de refactorisation est double : \begin{enumerate}
           \item Les résultats précédents ont pu être consolidés avec la généralisation du
               tableau \ref{tab:tstfinal} sur un seul bâtiment à l'ensemble du quartier étudié \ref{fig:heatmap}, sans que cette tâche soit rendue fastidieuse par une implémentation de code perfectible.
           \item Il est désormais possible de développer de nouveaux modèles ou de consolider celui existant en s'appuyant sur le projet actuel, sans avoir à en commencer un nouveau.
        \end{enumerate}

    \subsection{Vers un pipeline CI/CD simple}\label{subsec:vers-un-pipeline-ci/cd-simple}

\begin{lstlisting}[language=YAML, caption={Fichier \texttt{.gitlab-ci.yml} d'IBIS},label={lst:cicd}]
# GitLab CI/CD pipeline for the IBIS project
# The base image only provides Python 3.12, used solely to bootstrap uv.
# uv then downloads and manages the actual Python 3.13.7 runtime.

stages:
  - test

variables:
  UV_PYTHON_VERSION: "3.13.7"
  UV_CACHE_DIR: "$CI_PROJECT_DIR/.uv-cache"

unit_tests:
  stage: test
  image: python:3.12-slim

  cache:
    key: "$CI_COMMIT_REF_SLUG"
    paths:
      - .uv-cache/

  before_script:
    # Install uv with standalone installer
    - apt-get update -qq && apt-get install -y -qq curl ca-certificates
    - curl -LsSf https://astral.sh/uv/install.sh | sh
    - export PATH="$HOME/.local/bin:$PATH"
    - uv --version
    # Install and pin the required Python version through uv
    - uv python install "$UV_PYTHON_VERSION"
    - uv python pin "$UV_PYTHON_VERSION"

  script:
    # Install project dependencies (respects uv.lock if present)
    - uv sync --frozen
    # Run tests
    - uv run python tests/unit_test.py

default:
  tags:
    - python

  artifacts:
    when: always
    paths:
      - .uv-cache/
    expire_in: 1 week\end{lstlisting}

    \begin{bluebox}
        Ce test simple ne permet évidemment pas de couvrir l'ensemble du code et des fonctionnalités d'IBIS, bien qu'il détecte un certain nombre de dysfonctionnements simples, notamment sur la résolution d'équations différentielles par le solveur GreyBox, étape du projet la plus complexe.
        Les tests plus complets ne sont pas ajoutés en raison des limitations techniques de l'instance GitLab du CEA, en particulier à cause du nombre limité de runners disponibles\footnote{Des travaux sont en cours pour intégrer d'autres runners à l'échelle Institut ou Laboratoire.}.
        En effet, un seul runner étant accessible à l'échelle CEA, celui-ci a un timeout capé à 30 minutes, empêchant le lancement de tests plus longs comme MEBM et AMSBP\@.
    \end{bluebox}
