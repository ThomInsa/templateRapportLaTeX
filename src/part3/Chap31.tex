un plus grand volume de données et différents modèles dans un second.

    L'arborescence du projet ébauchée, l'étape suivante est l'inspection des fonctions pour vérifier leur propreté, leur maintenabilité et la facilité à les faire évoluer.
    Autant que possible, ce procédé tente de s'appuyer sur les recommendations du livre de Robert C. Martin \cite{clean_code}, faisant figure de référence standardisée dans le milieu du développement du logiciel.

Le nombre de bonnes pratiques décrites dans cet ouvrage est particulièrement élevé et toutes ne sont pas forcément applicables simultanément, en particulier les exemples sont souvent tirés du développement web, un domaine généralement éloigné du calcul scientifique.
La synthèse la plus élémentaire des techniques de nettoyage du code donnée plus bas a tout de même guidé le développement et les réflexions autour d'\gls{IBIS} :

    \begin{itemize}
        \item Le nommage des variables doit être explicite.
        En particulier, allonger le nom d'une variable est généralement une bonne idée même si sa lecture peut sembler fastidieuse.
        \item Les fonctions, classes, méthodes et fichiers doivent être le plus court possible (une dizaine de lignes maximum) et chaque fonction doit remplir un seul objectif.
        En général, si une fonction dépasse ce nombre de lignes, alors elle peut être séparée.
        \item De même, le nombre de paramètres d'une fonction ne doit pas être supérieur à trois.
        \item Le \gls{TDD} reste la meilleure approche à la quasi-totalité des problèmes de programmation, aussi l'utilisation des tests doit être aussi fréquente que possible
        \item Les commentaires doivent être utilisés avec parcimonie et ne remplacent en aucun cas l'explication du code par lui-même.
        La raison d'être de nombreux commentaires est en effet la clarification d'éléments de code mal implémentés, avec pour finalité la présence dans le projet de deux informations floues plutôt qu'une explicite.
    \end{itemize}

    \begin{bluebox}
        (05/02) : Ces bonnes pratiques ne sont pour l'instant pas étendues à l'ensemble du projet \gls{IBIS}, encore à un stade très précoce de développement.
    Elles sont néanmoins appliquées par endroit et nourrissent les réflexions pour la création des issues notamment\textit{(voir chapitre \ref{ch:versionning-et-gestion-de-projet})}.
        Par ailleurs, d'autres conseils de développement propres spécifiques au langage Python sont données dans \cite{serious_python} mais n'ont pas été explorées à ce jour.
    \end{bluebox}
